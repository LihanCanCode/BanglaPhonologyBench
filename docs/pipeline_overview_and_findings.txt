BanglaPhonologyBench + GTAD/STAD Analysis — Pipeline, Prework, and Findings
============================================================================
Generated as a working reference for idea generation / thesis writing.
Full technical detail always lives in CLAUDE.md, the Research Spec, and
docs/DEVELOPMENT_LOG.md — this file is a narrative summary of all of it.


1. WHAT THIS PROJECT IS
------------------------------------------------------------------------
BanglaPhonologyBench is a phonology benchmark for Bangla language models
(G2P, syllable counting, rhyme judgment/generation, schwa-deletion
prediction), combined with a tokenization-misalignment analysis specific
to Bangla's abugida script. It replicates and extends two prior papers:

  - PhonologyBench (Suvarna et al., 2024) — the task design (G2P,
    syllable counting, rhyme).
  - "How Tokenization Limits Phonological Knowledge Representation in
    LMs" (Liao & Shi, 2026) — the probing protocol and the STAD metric,
    which this project lifts from the character level (their alphabetic
    scripts) up to the akshara level (Bangla's grapheme clusters).

The core idea: Bangla is written in an abugida where a single visual
"syllable-like" unit (an akshara — e.g. a conjunct consonant cluster
plus vowel sign) can span multiple Unicode codepoints and, critically,
can straddle a tokenizer's subword boundaries in ways that alphabetic
scripts never do. This project asks: does that tokenizer-vs-script
mismatch measurably hurt a language model's internal representation of
Bangla phonology, and does it hurt zero-shot phonological task
performance?


2. THE CORE METRIC TRIPLE (do not change definitions casually)
------------------------------------------------------------------------
Hierarchy: bytes ⊂ codepoints ⊂ aksharas ⊂ syllables.

  GTAD  (Grapheme-Tokenization Alignment Divergence), in [0,1]
        Fraction of a tokenizer's internal boundaries that cut INSIDE an
        akshara (violate its integrity) — decomposed into byte-internal,
        matra-split, and conjunct-split violation types. GTAD is exactly
        0 for genuinely alphabetic scripts by construction, so it
        isolates the abugida-specific misalignment axis. This is the
        project's own contribution (Liao & Shi don't need it, since
        English has no akshara-like clustering).

  STAD_bn (Syllable-Tokenization Alignment Divergence, Bangla variant)
        Hamming distance between the true syllable-boundary vector and
        the tokenizer-boundary vector, measured over the m-1 gaps
        BETWEEN aksharas (not between codepoints), normalized by (m-1).
        None when m<2 (single-akshara words). This is Liao & Shi's STAD
        lifted from codepoint-gaps to akshara-gaps; it collapses back to
        their original definition when every akshara happens to be one
        codepoint (i.e. for alphabetic scripts).

  rho (ρ), in [0,1]
        Fraction of TRUE phonemic syllable boundaries that have no legal
        akshara-gap they could possibly land on (e.g. the syllable break
        in /shan.to/ falls inside the conjunct ন্ত of শান্ত — no tokenizer,
        however script-aware, could place a boundary there without
        breaking the akshara). This is a property of the Bangla script
        itself, not of any tokenizer — it's the ceiling on what ANY
        akshara-respecting tokenizer could ever achieve on STAD.

These three are always reported together, never collapsed into one
number, because they answer different questions: GTAD = "does the
tokenizer even respect orthographic units?", STAD = "even when it does,
does it get the phonology right?", rho = "how good could STAD possibly
get, given the script?".

WORD CATEGORIES (used everywhere downstream — probing, zero-shot splits):
  A  (Aligned)          GTAD=0 AND STAD=0   — clean case
  M  (syllable-Misaligned) GTAD=0 AND STAD>0.25 — akshara-respecting but
                          wrong syllable boundaries
  CB (Cluster-Broken)    GTAD>0              — tokenizer literally cuts
                          inside a conjunct/matra, the worst case

The central hypothesis of the whole project: a model's phonological
competence (whether probed from hidden states or measured by zero-shot
accuracy) should degrade going A > M > CB.

4. MILESTONE-BY-MILESTONE STATUS
------------------------------------------------------------------------

M1 — Foundations (DONE)
  - Lexicon: Google bn-BD, 65,037 entries, CC BY 4.0.
  - Akshara segmenter + phonemic syllabifier validated: 96 tests,
    99.86% syllable-count agreement against the lexicon.
  - Orthography->phoneme aligner: 99.95% coverage (31 residual failures,
    heterogeneous long tail — English-loan অ্যা-digraph transliteration,
    archaic double-consonant spellings, proper-name hiatus).
  - Earlier in-session bug: anusvara/khanda-ta were being consumed BEFORE
    the vowel instead of after in the aligner — a real Spec-compliance
    bug, fixed same day, coverage jumped 86.85% -> 89.44% (then further
    to 99.95% with later fixes).

M2 — Tasks 1-2 + real-tokenizer metrics (DONE)
  - g2p.jsonl and syllable_count_word.jsonl frozen: 3,000 words each,
    1,500 HighFreq/1,500 LowFreq by wordfreq(bn) zipf quartile.
  - GTAD/STAD/rho computed for 5 real tokenizers on the top-3000 list
    (results/metrics_top3000.csv), descriptive stats in figures/figure2.
  - Real tokenizers are dramatically worse than the Spec's illustrative
    "SIMULATED" tables suggested — e.g. Llama-3.1 GTAD as high as 0.86 on
    some words vs. the SIMULATED table's 0.5. This was an early signal
    that the phenomenon is real and large, not a modeling artifact.

M3 — Tasks 1, 3a, 3b, 4 + full human annotation pass (DONE)
  - Task 3a (rhyme pairs): 200 positive + 200 negative (negatives split
    80 assonance_decoy / 40 ortho_decoy / 80 random), anti-leakage via
    is_trivial_pair + phoneme-stem checks. Human-verified 400/400, 100%
    agreement.
  - Task 3b (rhyme generation): 300 prompts (200 common/100 rare), gold
    sets additionally filtered through is_trivial_pair — WITHOUT this
    filter, short grammatical suffixes like -এর dominate gold sets almost
    entirely (a real methodological finding, documented in the script's
    docstring). Human-verified 300/300, no corrections.
  - Task 4 (schwa deletion): 1,000 words, environment-stratified. Human-
    verified 160/160 (stratified sample), 100% agreement.
  - Task 1 (etymology): 4-way tag (added "deshi" beyond the Spec's
    original 3). Human-verified 353/353. Heuristic tagger accuracy only
    38.2% — a genuine, reportable weakness of orthography-only etymology
    guessing (i.e. the heuristic is a bad G2P-adjacent baseline, not a
    bug in the annotation).
  - No inter-annotator kappa anywhere — single annotator throughout, a
    documented limitation vs. the Spec's original 2-annotator design.

M4 — Probing pipeline (BUILT + RUN for the 2 script-aware tokenizers)
  - Pivoted away from forking liaodisen/Tokenization-Phonology (the
    Liao & Shi reference repo) after inspecting it: its extraction code
    was simple enough to reimplement directly, and its probe-training
    scripts are hardcoded to exactly TWO conditions (their good/bad
    Hamming-distance split) plus English-only filenames — not reusable
    for a three-way A/M/CB split without a rewrite anyway. Built instead:
    scripts/kaggle_probing_lib.py (file-level-resumable extraction +
    a generalized N-category probe battery: RidgeCV for regression
    targets, LogisticRegression for classification, 10 seeds, 80/20
    split, random-label/embedding controls, automatic pairwise one-sided
    t-tests) — unit-tested with a mock model, no GPU needed to validate
    logic.
  - Two real bugs found and fixed on the first actual Kaggle GPU runs
    (both are useful lessons, see section 6 below):
      1. T5-family models (BanglaT5, ByT5) overflow to inf in float16 —
         T5 was trained in bf16/fp32; fixed by forcing float32 for the
         T5 family regardless of device.
      2. Storage dtype float16 was too narrow for some real hidden-state
         values (word বীর্য, layer 4, exceeded float16's ~65504 max even
         though the values were finite in the model's native dtype) —
         fixed by defaulting checkpoint storage to float32.
      3. (Found and fixed THIS session, not yet in CLAUDE.md's numbered
         list) A third, more subtle bug: the g2p (phon_vec) probe's
         reported R^2 was astronomically wrong (~1e28 to 1e32) even
         though the embeddings themselves were finite and correct. Root
         cause: phon_vec is zero-padded to the dataset-wide max length
         (18), so within a single A/M/CB category slice, tail columns
         can be ~all-zero except for one or two rare long words.
         Per-column z-score normalization by that column's near-zero std
         blew those rare nonzero values up to huge normalized targets,
         destabilizing RidgeCV, and sklearn's default unweighted
         per-column R^2 average let a couple of wrecked columns drag the
         whole score down to nonsense. Fixed by (a) dropping columns that
         are constant across a whole category before fitting, and
         (b) switching to variance-weighted R^2 aggregation as a second
         safety net. Verified against a purpose-built regression test
         reproducing the exact padded-sparse-column scenario.
  - BanglaT5 + TigerLLM probing run to completion post-fix (results in
    results/BanglaT5 & TigerLLM.csv). GPT-2/ByT5/Llama-3.1 extraction
    also ran, but their probe comparison could not be trained (see
    Finding 3 below) — this is expected, not a failure.
  - Rhyme-probe (Task 3a) A/M/CB category join: BUILT and RUN to
    completion for BanglaT5 + TigerLLM (results/probe_pairwise_
    BanglaT5+TigerLLM.csv). Result is genuinely mixed, not a clean A>M>CB
    confirmation — see Finding 4a below.
  - Pairwise one-sided p-values (A>M>CB) aggregated into
    results/probe_pairwise_summary.csv, ready for Table-3-style
    reporting.
  - Not yet run: GPT-2/ByT5/Llama-3.1 g2p/syllable-count probing
    (expected ~all-CB per Finding 2/3, low priority but not zero-value
    for completeness).

M5 — Zero-shot evals + human baselines + regression analysis + writing
  (BASELINES DONE, TigerLLM ZERO-SHOT RUN + REGRESSION DONE, rest pending)

5. KEY FINDINGS SO FAR (useful for the "ideas" ask)
------------------------------------------------------------------------

Finding 1 — Real tokenizers are far worse than illustrative estimates.
  The Spec's own illustrative SIMULATED tokenizer tables understated the
  problem; real GPT-2/Llama-3 GTAD values run as high as 0.86 on real
  words. This alone is a strong opening result: Bangla tokenization is
  measurably, severely misaligned with script structure in tokenizers
  that were never designed with Bangla in mind.

Finding 2 — Category counts are a headline result on their own, before
any probing/zero-shot numbers exist:

  tokenizer  |   A   |   M    |   CB   | excluded (of 3,000)
  -----------|-------|--------|--------|---------------------
  llama3     |     0 |      0 |  2,982 | 18
  gpt2       |     0 |      0 |  2,982 | 18
  byt5       |     0 |      0 |  2,982 | 18
  tigerllm   |   697 |    671 |  1,614 | 18
  banglat5   |   647 |  1,822 |    442 | 89

  Every English-centric tokenizer (llama3, gpt2, byt5) puts 99%+ of
  Bangla words in the worst (cluster-broken) category. GTAD ≡ 0 is a
  theoretical property of alphabetic scripts, but the flip side —
  "GTAD > 0 for almost every word" — is what actually happens when you
  point a script-unaware tokenizer at an abugida. TigerLLM and BanglaT5
  (Bangla-aware tokenizers) show genuine spread across all three
  categories, which is exactly why only those two could run the A/M/CB
  probe comparison at all.

Finding 3 — The probe comparison is only meaningful for
  script-aware tokenizers, structurally, not just empirically. Because
  gpt2/byt5/llama3 have (effectively) zero A and M words, there is
  nothing to compare their CB-category embeddings against — not a
  missing-data problem to patch, but itself the finding: for these
  tokenizers, "does tokenization misalignment hurt phonological
  encoding?" isn't even an answerable question in a within-tokenizer
  sense, because misalignment isn't a variable for them — it's a
  constant. The comparison across tokenizers (Bangla-aware vs. not)
  becomes the real story instead of within-tokenizer A/M/CB comparison.

Finding 4 — Where probing DID run (BanglaT5, TigerLLM), results broadly
  support the A > M > CB hypothesis for syllable-count probing:
    BanglaT5, final layer (12): A=0.698 > M=0.599 > CB=0.436
    TigerLLM, final layer (48): A=0.689 > CB=0.595 > M=0.541  (M/CB
      order swapped, plausibly noise from unequal category sizes —
      p-values now aggregated in results/probe_pairwise_summary.csv,
      worth a direct significance read before citing this ordering)
  G2P (phon_vec) probing, by contrast, is negative across nearly every
  layer/category for both models — plausibly a property of the probe
  DESIGN (phon_vec is a vector of arbitrary categorical phoneme-vocab
  indices; linear regression on categorical IDs has no strong reason to
  work well, since index 5 isn't numerically "between" index 4 and 6 in
  any phonetic sense) rather than evidence the models don't encode
  phonology at all — the syllable-count task (a genuinely ordinal
  target) on the SAME embeddings works fine, which argues for a probe
  design issue over a representation issue. Possible idea: try a
  classification-style probe (predict each phoneme slot independently
  via LogisticRegression, or use a Hamming/edit-distance-based score
  instead of R^2) as a fairer comparison to Liao & Shi's own STAD-style
  scoring, since R^2 on unordered categorical targets is a known-shaky
  metric.

Finding 5 — Task 3b's naive design would have been dominated by
  grammatical suffixes. Building the rhyme-generation gold sets without
  filtering through is_trivial_pair (stem/phoneme-sequence overlap
  check) let short, extremely productive suffixes like -এর swallow the
  gold set almost entirely — not a useful task if left in. This is a
  general lesson about rhyme/phonology tasks in agglutinative-adjacent
  languages: naive "shares a rime" gold-set construction conflates
  morphological productivity with genuine phonological rhyme.

Finding 6 — Etymology tagging from orthography alone is weak (38.2%
  heuristic accuracy against 353 human-verified gold labels). Could be
  read two ways for the thesis: (a) a clean negative result supporting
  "you need more than script-level information," or (b) grounds for an
  interesting follow-up — does a language model's zero-shot etymology
  guess also cluster around 38%, or does it do meaningfully better/worse
  than the orthography-only heuristic? That'd be a nice small addendum
  to the M5 zero-shot battery if there's room. (Still not run.)

Finding 4a — The rhyme-probe (Task 3a) result, once run, does NOT confirm
  A>M>CB either, in a specific and consistent way across both models:
    BanglaT5 rhyme: CB beats M in ~92% of layers (opposite of M>CB)
    TigerLLM rhyme: CB beats M in ~71% of layers (also opposite)
  Combined with the g2p/syllable-count probing swap noted in Finding 4,
  the overall M4 probing picture is: real signal exists (probes clearly
  beat the random-embedding control), but the specific A>M>CB ORDERING
  the Spec hypothesized doesn't hold cleanly for any task/model combo
  checked so far. This deserves its own paragraph in the thesis rather
  than being smoothed over — "misalignment matters, but not in the simple
  monotonic way we predicted" is a more honest and more interesting claim
  than either confirming or rejecting the hypothesis outright.

Finding 7 — M5's zero-shot pass (TigerLLM-9B-it, Bangla prompts, all 5
  tasks at full scale) produces a genuinely uneven, task-by-task picture,
  not a single "the model is good/bad at phonology" verdict:

    Task              | Baseline           | TigerLLM zero-shot        | Read
    ------------------|--------------------|-----------------------|------
    G2P               | 17.6% PER,36.2% ex | 3.0% PER, 93.6% exact  | Model dramatically beats baseline
    Syllable count    | 31.9% exact        | 100.0% exact           | Perfect -- needs Finding 7b's caveat
    Rhyme awareness   | 100% (oracle)      | 53.0% acc, F1 0.236    | Near chance, biased toward "na" (no)
    Rhyme generation  | 100% (oracle)      | success@5 = 0.21       | Far below the dictionary ceiling
    Schwa deletion    | 77.1% per-position | 52.4% per-position     | WORSE than a 1-line heuristic

  The "oracle" baselines for rhyme (both tasks) assume perfect
  pronunciation knowledge (a dictionary lookup) -- they're a ceiling
  reference, not a floor a model should be expected to clear; TigerLLM's
  numbers there should be read as "far from ceiling," not "far below a
  fair competitor."

Finding 7b — The rho-ceiling analysis (scripts/analyze_rho_ceiling.py)
  strengthens, rather than resolves, the syllable_count contamination
  question: TigerLLM scores 1.000 in every rho bin, INCLUDING rho=1.0
  (221 words where the true syllable boundary has literally no possible
  orthographic representation). Genuine spelling-based reasoning should
  degrade there; it doesn't, at all. This is a specific, falsifiable
  point for the thesis -- stronger than "100% just looks suspicious" --
  and raises the priority of the still-not-run nonce-word contamination
  test (generate words that cannot appear in any training corpus and see
  if the perfect score survives).

Finding 8 — The GTAD/STAD/rho regression (scripts/analyze_regression.py,
  run for all 4 non-degenerate tasks) finds NO universal, uniformly-signed
  story -- a materially different, more defensible result than the
  task-by-task predictions a naive reading of the Spec's hypothesis (or
  an external planning document, see docs/ideas2.md) would make:

    Task             | n     | GTAD    | STAD    | rho     | log_freq | R^2
    -----------------|-------|---------|---------|---------|----------|------
    G2P              | 2,982 | -0.338  | +0.203  | +0.142  | -0.229   | 0.022
    Schwa deletion   |   999 | +0.146  | -0.142  | -0.218  | +0.042   | 0.014
    Rhyme awareness  |   386 | +0.198  | -0.079  | -0.149  | +0.283   | 0.023
    Syllable count   | 2,982 | degenerate (0 outcome variance)          | --

  GTAD is negative for G2P (matches the naive hypothesis) but POSITIVE
  for schwa and rhyme. STAD/rho are negative for schwa/rhyme (matches
  hypothesis) but POSITIVE for G2P. Every R^2 is small (never above
  0.023). A/M/CB category breakdowns tell the same story at a coarser
  grain -- never a clean A>M>CB or even A>CB ordering in ANY of the four
  tasks (e.g. g2p: A=0.927, CB=0.930, M=0.958 -- CB is not worse than A).
  Tokenization misalignment has small, real, task-specific -- not
  uniformly directional -- effects on zero-shot generation. This is a
  genuinely different mechanism-level claim than M4's probing story (see
  the Synthesis section below for why that's not a contradiction).

Finding 9 — The G2P "frequency paradox" (log-frequency negatively
  predicting accuracy, opposite of PhonologyBench/most psycholinguistic
  literature) is partially, not fully, a word-length confound: rarer
  words in this dataset skew longer (tatsama compounds), and longer words
  are slightly EASIER for exact-match G2P (+0.099 correlation).
  Controlling for length shrinks the log_freq coefficient from -0.229 to
  -0.121 (roughly halves) and length becomes the single strongest
  predictor in the model (+0.401). A residual negative frequency effect
  survives, though -- not fully explained away.

  DIRECTLY TESTED via etym-stratified accuracy (same session, follow-up):

    Etymology  | n     | Accuracy | Mean length | Mean log_freq
    -----------|-------|----------|--------------|---------------
    Tadbhava   | 1,660 |   0.926  |     6.11     |     3.11
    Tatsama    | 1,166 |   0.947  |     8.28     |     3.02
    Foreign    |   142 |   0.951  |     7.01     |     2.92
    Deshi      |    14 |   1.000  |     6.86     |     2.58   (n too small)

  Tatsama beats tadbhava (94.7% vs 92.6%) despite being longer and no
  more frequent -- length riding along doesn't explain the gap away,
  since tatsama is both longer AND more accurate. A user-supplied
  Wikipedia claim ("Bangla orthography is opaque for tatsama, transparent
  for tadbhava," neither independently verified this session) appears to
  cut the other way on first read -- reconciled cautiously, not
  dismissed: "opaque" there plausibly describes reading difficulty for a
  human unfamiliar with Sanskrit/conjunct spelling conventions, a
  different axis from "rule-governed once a model has seen enough
  examples," which is what matters for exact-match generation accuracy.
  Tadbhava's exception-laden colloquial sound-drift (irregular schwa
  deletion, assimilation) may be the harder EXACT-MATCH target precisely
  because it's less rule-governed, not because tatsama is more
  accessible. Flagged as an interpretation for the thesis to state
  carefully, not a settled resolution of the literature tension.


6. LESSONS FROM DEBUGGING (useful for avoiding repeat mistakes)
------------------------------------------------------------------------
  - Always unit-test GPU-bound pipeline code with a MOCK model before
    spending real GPU quota on it (this is exactly why
    kaggle_probing_lib.py has a full mock-model test suite that runs in
    seconds locally) — it doesn't catch numerical-precision bugs
    (float16 overflow) that only show up on real model outputs, but it
    does catch every structural/logic bug for free.
  - float16 is unsafe for storing or computing T5-family hidden states;
    T5 was trained in bf16/fp32. This generalizes: always check a
    model's *training* dtype before choosing an *inference* dtype,
    don't assume fp16 is a safe default just because it halves memory.
  - Padded/sparse targets (zero-padding a variable-length vector to a
    fixed max length) are dangerous to normalize per-column without
    checking for near-zero variance first — a handful of legitimate
    outliers in an otherwise-constant column can silently produce
    catastrophically unstable regression fits. Worth checking for this
    pattern anywhere else padding is used in this pipeline (e.g. if a
    similar padded vector target ever gets used for the rhyme or schwa
    probes later).
  - Astronomically bad metric values (R^2 in the 1e28+ range) are a
    strong signal of numerical instability upstream, not "the model is
    just really bad at this" — a sane model badly failing a task
    produces R^2 around -1 to -5, not -1e30. Worth remembering as a
    smell test for any regression-based eval.
  - A LITERALLY PERFECT score (100.0%, zero errors, on hundreds+ of
    diverse items) is itself a red flag, in the opposite direction from
    the usual "why is this broken" instinct — real zero-shot systems
    essentially never hit perfect scores on a large, diverse item set,
    especially against gold labels that aren't even internally
    100%-self-consistent (M1's own syllable-count validation only
    reached 99.86% agreement). Don't just accept a suspiciously clean
    number because the pipeline ran without errors — independently
    re-verify (random sample eyeball, full mismatch scan, distribution
    comparison) before trusting it, exactly the "read samples as a
    native speaker" discipline this project used for the rhyme/schwa
    annotation passes too. In this project's case (M5 syllable_count),
    independent re-verification RULED OUT a scoring bug but couldn't
    rule out training-data contamination — see Finding 7b.
  - A local scoring/analysis cell that reuses the same variable (e.g.
    SAMPLE_SIZE) for both "how much to generate" and "how much to score"
    will silently under-report results once generation has moved past
    that cap — a real bug hit mid-session (g2p briefly showed n=1500 in
    the scoring table despite 2,341+ completions existing on disk).
    Whenever a script slices a dataset for a quick test run, double-check
    that slicing isn't ALSO capping the final scoring pass once the real
    run finishes.
  - Iterative manual file downloads (Kaggle -> local disk, repeated
    across several back-and-forth rounds) reliably produce stale
    duplicates and misplaced files (wrong folder, wrong extension, old
    partial-scale copies sitting next to new full-scale ones under
    similar names) — worth a deliberate cleanup pass (verify by line
    count / max id, delete stale copies, rename to one canonical scheme)
    before trusting "the data is all there," not just before committing.

8. SYNTHESIS — What TigerLLM Has (and Hasn't) Learned About Bangla Phonology
------------------------------------------------------------------------
Draft narrative for the M5 results chapter, written directly from the
numbers in Findings 7-9 above. Treat this as a first draft to edit, not a
finished chapter — it hasn't been checked by a second pair of eyes, and
two of its claims (the syllable_count "genuine competence" reading, the
tadbhava/tatsama story for the frequency paradox) are explicitly flagged
below as pending verification, not settled.

8.1 The headline result: uneven competence, not a single verdict

Across five tasks probing different facets of Bangla phonological
knowledge, TigerLLM-9B-it's zero-shot performance is not well described
by either "the model knows Bangla phonology" or "the model doesn't."
It is good at some things and genuinely bad at others, and the split
is informative:

  STRONG:  G2P (93.6% exact, PER 0.029) — crushes the naive baseline
           (36.2% exact, PER 0.176) by a wide margin.
  UNCLEAR: Syllable counting (100.0% exact) — perfect, but flagged with
           a contamination caveat (Finding 7b) pending the nonce-word
           test. Cannot currently be cited as either a clean win or a
           clean artifact.
  WEAK:    Rhyme awareness (53.0% acc, F1 0.236) — barely above chance
           on a balanced set, systematically biased toward "na" (no).
  WEAK:    Rhyme generation (success@5 = 0.21) — far below the
           dictionary-lookup ceiling (100%, by construction).
  FAILING: Schwa deletion (52.4% per-position) — WORSE than a one-line
           majority-rule heuristic (77.1%). Not just "not great" — the
           model actively underperforms a hardcoded rule a human wrote
           in five minutes.

8.2 Why the asymmetry? A candidate explanation (needs scrutiny before
    it goes in a final draft)

The clearest dividing line in the data is between G2P (strong) and
everything phonology-adjacent-but-not-G2P (weak-to-failing). A plausible
account:

  - G2P is close to a direct, learnable function of orthography. Bangla
    spelling is largely phonemic; grapheme-to-phoneme mapping, while it
    has real irregularities (schwa deletion, silent letters, conjunct
    simplification — exactly the phenomena bangla_phonology.py's aligner
    has to model explicitly), is still fundamentally "read the word,
    say the sounds." A model that has seen enough Bangla text plausibly
    absorbs this mapping the way it absorbs spelling-to-pronunciation
    patterns in any language it's trained on.

  - Schwa deletion requires the SAME underlying knowledge (it's a
    sub-problem of G2P — deciding whether one specific vowel is
    pronounced) but the zero-shot elicitation here asks for it in
    ISOLATION, per-consonant, without the full-word context a G2P
    prompt provides. That the model does much worse at "is this one
    schwa pronounced" than at "transcribe the whole word" (where it
    implicitly gets schwa deletion right as part of getting the whole
    IPA string right, 93.6% of the time) suggests the knowledge may be
    context-bound rather than an explicit, extractable rule — worth
    checking directly: how often does the model's OWN g2p output for a
    word imply a different schwa-deletion pattern than its answer to
    the isolated schwa_deletion prompt for the same word? That
    comparison hasn't been run and would be strong evidence either way.

  - Rhyme judgment requires comparing two words' PHONOLOGICAL structure
    abstractly (same rime, independent of spelling) rather than reading
    off one word's own pronunciation. The "na" bias suggests the model
    may default to a conservative "not obviously the same" heuristic
    rather than actually computing and comparing rimes — consistent
    with rhyme being a qualitatively different kind of task (comparison/
    abstraction) rather than a harder version of the same kind of task
    (transcription).

8.3 What the regression adds (and complicates)

Finding 8's regression result cuts against a tidy "GTAD explains
everything" story. If tokenization misalignment were the primary driver
of these failures, GTAD/STAD/rho should predict difficulty consistently
across tasks. They don't — the direction of the effect flips between G2P
and schwa/rhyme, and every effect size is small (R^2 < 0.023 throughout).
This suggests **tokenization misalignment is a real but minor factor**
here — not the reason schwa deletion and rhyme judgment fail. Whatever
IS the primary driver of those failures (task framing, the isolated-vs-
contextual elicitation difference in 8.2, insufficient training signal
for abstract phonological comparison, something else) is not yet
identified — flagged honestly as an open question rather than
retrofitted to whichever metric happened to be on hand.

This is also NOT a contradiction of the M4 probing results (which broadly
found real signal, and closer to the predicted A>M>CB pattern) once you
separate the two mechanisms: M4's probes read ONE frozen last-token
hidden state, whose content is mechanically shaped by where the tokenizer
placed its boundaries. M5's zero-shot generation attends over the WHOLE
input regardless of internal boundary placement. There is no a priori
reason misalignment has to bottleneck both the same way, and the data
here suggests it doesn't: TigerLLM's zero-shot accuracy is ALSO flat
across its own A/M/CB categories (Finding 8), even though M4 found real
(if imperfectly-ordered) probing differences between those same
categories. Tokenization misalignment may matter more for what a frozen
representation contains than for what an autoregressive model can
eventually produce given enough attention over the full context — a
genuinely interesting methodological point connecting M4 and M5, not
just two separate results sitting next to each other.

8.3a Etym-stratified G2P accuracy: DONE, and it supports the length/
     regularity story rather than contradicting it

Tatsama accuracy (94.7%, n=1,166) beats tadbhava (92.6%, n=1,660) despite
tatsama words being both longer (8.28 vs 6.11 mean phonemes) AND no more
frequent (log_freq 3.02 vs 3.11) — so this isn't length riding along
uncontrolled, it's etymology itself predicting accuracy in the direction
8.2/Finding 9 proposed. A user-supplied Wikipedia claim during this
session ("Bangla orthography is opaque for tatsama, transparent for
tadbhava" — not independently verified here) reads as tension on first
pass; reconciled cautiously rather than dismissed: that claim plausibly
describes READING difficulty for a human unfamiliar with Sanskrit/
conjunct spelling conventions, a different axis from RULE-LEARNABILITY
for a model that has seen enough tatsama examples. Tadbhava's
exception-laden colloquial sound-drift (irregular schwa deletion,
assimilation patterns) is plausibly the harder EXACT-MATCH target
precisely because it's less rule-governed, not because tatsama is more
accessible in the everyday-reading sense the Wikipedia claim addresses.
State this as an interpretation the thesis offers, with the literature
tension named explicitly, not as a resolved contradiction.

8.4 What would strengthen this chapter, in priority order

  1. The nonce-word contamination test (Finding 7b above) — turns

     result or an honest documented limitation. Currently the single

  2. The g2p-vs-isolated-schwa consistency check proposed in 8.2 — cheap

  3. DONE: etym-stratified G2P accuracy (8.3a above) — tatsama > tadbhava,

     written, though — neither source was read firsthand this session.

  5. Human baseline numbers — lets "53% is near chance" and "52.4% is
